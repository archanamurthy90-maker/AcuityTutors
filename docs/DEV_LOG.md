## Architecture Overview

- **Frontend:** React + Vite provides student sign-in, targeted practice, attempt feedback, progress history, and a tutor roster dashboard.
- **Backend:** Express exposes `/api` routes, validates requests, enforces JWT-based identity and role/ownership checks, and serves the built frontend in production.
- **Persistence:** PostgreSQL stores users, tutor/student profiles, roster relationships, subjects/topics, attempt history, mastery snapshots, and generated practice questions. Prisma owns the schema and migrations. Docker Compose provides local PostgreSQL; Cloud SQL is the planned production database.
- **Mastery:** A deterministic server-side service computes a per-student/per-topic 0-100 score from quiz-attempt history and stores the latest snapshot. The exact initial scoring rule should be explicit and unit-tested; AI does not determine the numeric score.
- **Gemini:** Server-only integration generates a new question, answer, and explanation using the student's topic and mastery-derived difficulty. A separate tutor-summary call turns roster mastery data into concise plain language. Validate structured model output and handle provider failures.
- **Security:** Hash passwords, keep JWT and Gemini secrets out of client code, validate inputs, and restrict student/tutor data by role and ownership.

## Proposed Database Schema

| Model | Key fields and relationships |
|---|---|
| `User` | `id`, unique `email`, `passwordHash`, `role` (`STUDENT` or `TUTOR`), timestamps. One optional one-to-one profile in `Student` or `Tutor`. |
| `Student` | `id`, unique `userId`, `displayName`, timestamps. Relates to roster memberships, quiz attempts, mastery scores, and generated practice questions. |
| `Tutor` | `id`, unique `userId`, `displayName`, timestamps. Relates to roster memberships. |
| `TutorStudent` | Join model with `tutorId`, `studentId`, `createdAt`; unique `(tutorId, studentId)`. This supports multiple tutors per student and a roster per tutor. |
| `Subject` | `id`, unique `name`, timestamps. Has many topics. |
| `Topic` | `id`, `subjectId`, `name`, optional description, timestamps; unique `(subjectId, name)`. Has many attempts, mastery records, and practice questions. |
| `QuizAttempt` | `id`, `studentId`, `topicId`, optional `practiceQuestionId`, `isCorrect`, optional response/elapsed time, `difficulty`, `source`, `attemptedAt`. Each row is one answer attempt; append-only history is the source for progress. |
| `MasteryScore` | `id`, `studentId`, `topicId`, `score` (0-100), `attemptCount`, `confidence`, `computedAt`; unique `(studentId, topicId)`. Current snapshot derived from attempts, not a replacement for history. |
| `PracticeQuestion` | `id`, `studentId`, `topicId`, `prompt`, structured choices (JSON), `correctAnswer`, `explanation`, `difficulty`, `model`, `createdAt`. Generated by Gemini and optionally referenced by attempts. |

All models use generated primary keys and timestamps where appropriate. Foreign keys should have deliberate deletion behavior; historical attempts should not silently disappear if a topic or account is deactivated. Add indexes for roster lookup, student/topic attempt history ordered by `attemptedAt`, mastery lookup, and generated questions by student/topic and creation time.
